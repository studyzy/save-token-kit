## P0

### 1. content-encoding 完全未处理，"双轨"未落地

- **证据**：全 `src/` 检索 `content-encoding|gzip|zstd|inflate|brotli|decompress` 零命中；`src/proxy/server.ts:90-91` 直接 `rawBody.toString('utf-8')` 后 `JSON.parse`。
- **问题**：codex 实测会发 `content-encoding: zstd/gzip` 请求体。转发轨碰巧正确（原始字节原样转发），但解析轨崩坏：`JSON.parse` 失败 → 二进制乱码塞进 `capturedBodies` → 诊断漏计甚至"未找到主对话请求"。连锁：`isStreamingRequest`（server.ts:328-335）对压缩体误判为非流式 → mock 回退错误格式。
- **修复**：
  1. 引入解压依赖（gzip/deflate/br 用 Node 内置 `zlib`，zstd 需第三方如 `@napi-rs/zstd` 或等价物）；
  2. 在 server.ts 解析入口按 `content-encoding` 请求头解压出**副本**用于解析/捕获/落盘，转发保持原始字节（双轨）；
  3. `isStreamingRequest` 基于解压后副本判断；
  4. 无法解压的编码（未知算法）跳过解析并在报告中标注 `parseError`，不要塞乱码进 `capturedBodies`。

### 2. 优化失败任务被勾为 `- [x]`，污染状态机

- **证据**：`src/templates/skills/stk-optimize/SKILL.md:87` 写明"失败 → `- [x]` 外加注"。
- **问题**：`/stk` 从 tasks.md 勾选状态推导流水线阶段（stk/SKILL.md:26）。失败任务勾选后 tasks.md 全勾 → 误判"优化完成"进入 report → 产出"节省为 0"的误导性报告。
- **修复**：
  1. SKILL.md 规则改为：失败任务**保持 `- [ ]`**，在其后追加 `⚠️ 失败：<原因>`；
  2. `/stk` 状态推导规则同步：存在带失败标注的未勾项 → 显示"优化 ●（有 N 项失败）"，report 阶段报告中单列失败清单；
  3. 改完模板记得 `stk init --force` 刷新本机已装 SKILL。

## P1（架构）

### 3. PlatformAdapter 接口未收敛：可选字段矩阵 + instanceof 分叉

- **证据**：`src/adapters/platform-adapter.ts:43-148` 15+ 成员、10 个可选（`proxyRedirectArgs`/`probeEnvKeys`/`shouldIsolateConfigDir`/`isolatedProbeCredential`…）；`src/commands/diagnose.ts:111/135/198/247` 四处 `instanceof WorkBuddyAdapter` 分支 + 两段几乎重复的模型注入文案（111-139 与 191-228）。
- **问题**：多态退化为布尔矩阵，每接一个新平台就要在 diagnose.ts 通用流程里开一个洞。
- **修复**：按能力拆小接口（`Capturable` / `Probeable` / `Isolatable`），WorkBuddy 的模型注入/清理收敛为接口方法（如 `prepareCapture()` / `cleanupCapture()`），diagnose 按能力分派而非 instanceof。可在下个平台接入前偿还。

### 4. 平台特例硬编码泄漏进通用流程（含 1 个正确性 bug）

- **证据**：
  - `diagnose.ts:156` 硬编码 `const configDirVar = 'CLAUDE_CONFIG_DIR'`（Claude 平台事实）；
  - `diagnose.ts:320` 所有 agent 共用 `detectCodeBuddyVersion()`（命名即写死）；
  - **`diagnose.ts:441` `buildSpecContext` 无条件读 `~/.codebuddy/settings.json`——诊断 claude/codex 时 `plugin-enabled` 原语读到的是 CodeBuddy 的插件开关，跨平台取数错误**。
- **修复**：
  1. `configDirEnvVar` 挂到 adapter 接口上；
  2. `buildSpecContext` 改为从 adapter 获取 settings 文件路径（`adapter.getSettingsPath()`），plugin-enabled 原语按当前诊断 agent 的真实配置取数；
  3. 版本探测方法移入 adapter（如 `detectVersion()`）。

### 5. docs/architecture.md 严重失真

- **证据**：`docs/architecture.md:7` 命令列表缺 `uninstall`/`diff`；`:11` 声称 CodeBuddy 拦 `/v2/*`，实际 `codebuddy-adapter.ts:24` 是 `/v1`（`/v2` 属 WorkBuddy，workbuddy-adapter.ts:52）；`:16` 仍描述已删除的 `tools/registry.ts` + `impl/*` 自注册架构（零写死重构后为 `toolkits/data-registry.ts` + 声明式规格）；`:28` 适配器清单漏 WorkBuddy。
- **修复**：按当前代码重写该文档，重点同步：命令清单、各平台拦截路径、零写死后的 ToolkitSpec 数据驱动架构、四平台适配器清单。可在 CI 加一个轻量一致性检查（或至少在重构 PR 模板里加"是否需同步 architecture.md"检查项）。

## P1（proxy 安全与正确性）

### 6. live 模式完整 prompt 落盘，分享时无脱敏无警告

- **证据**：`server.ts:235` `prepareTrace` 写完整请求体到 `save-token/trace/<session>/`；`diagnose.ts:336-337` 写 `proxy-raw-body.json` 与含完整 mainBody 的 `diagnosis-report.json`。headers 已脱敏（server.ts:275-292）、`.gitignore` 已覆盖，但用户手动分享 trace/报告时无任何提示。
- **修复**：
  1. markdown 报告不内嵌原始 body（只保留统计与摘要）；
  2. trace 目录写一个 `SENSITIVE.md` 警示文件（"本目录含完整对话内容，分享前请脱敏"）；
  3. `proxy-raw-body.json` 改名或在报告头标注敏感级别。

### 7. 请求/响应无界缓冲 → OOM 风险

- **证据**：请求 chunks 无大小上限（server.ts:83-90）；trace 开启时响应 `respChunks` 无界且 `res.write` 忽略背压（server.ts:155-159）。
- **修复**：
  1. 请求体设上限（如 50MB）：超限转发原始流但跳过解析并标注 `bodyTooLarge`；
  2. trace 路径改用 `pipe`（非 trace 路径 server.ts:165 已用 pipe），或对响应也设上限；
  3. 尊重 `write()` 返回的背压信号。

### 8. 空 body 被静默丢弃（正确性 bug）

- **证据**：`server.ts:94` 与 `:177-178` 以 `if (bodyStr)` 判定——body 的 utf-8 解码为空字符串时 `forward.write(rawBody)` 被跳过，**上游收到空请求**；捕获同样跳过。
- **修复**：改判 `rawBody.length > 0`。

### 9. hop-by-hop 头与 trace 响应体处理不当

- **证据**：`server.ts:150` `{ ...req.headers, host }` 原样转发 `connection`/`keep-alive`/`transfer-encoding: chunked`；trace 模式响应 `content-encoding: gzip` 保留（server.ts:153），`finalizeTrace` 对压缩响应体 `JSON.parse` 必然失败落盘乱码（server.ts:249-253）。
- **修复**：
  1. 转发前剥离 hop-by-hop 头（connection 及其列出的头、transfer-encoding、keep-alive）；
  2. trace 时向上游请求 `accept-encoding: identity`，或落盘前按响应头解压副本。

### 10. 端口行为：EADDRINUSE 静默换随机端口

- **证据**：`server.ts:187-193`，依赖固定端口的用户脚本会连到错误服务且无感知。
- **修复**：换端口时输出黄色警告日志（"端口 X 被占用，已改用 Y"）。绑定 127.0.0.1 与 mock 隔离已正确，无需改。

## P1（SKILL 体系与交互）

### 11. stk-diagnose 第 1 步自动 `npm install -g`，违反自身哲学

- **证据**：`src/templates/skills/stk-diagnose/SKILL.md:11-17`"如未安装，先执行安装"。
- **问题**：全局 npm 安装是最重的系统级修改，却设在停点之前、无确认要求——直接违反"无显式确认不落地修改"的核心哲学。
- **修复**：改为检测到未安装时**先停点询问**（AskUserQuestion 或明确征询），用户确认后才执行 `npm install -g`；拒绝时给出手动安装指引并终止流程。

### 12. 6 对同名 agent 混淆风险：optimize 路由未锚定路径

- **证据**：stk-analyze 与 stk-optimize 的 agents 下 6 个重名（mcp-opt/memory-md/plugin-opt/rules-opt/skill-opt/tool-opt），语义相反（产建议 JSON vs 直接改配置）；链式推进时两套路由表同时留存同一会话上下文；optimize 路由只写 `@agents/` 未锚定 `../stk-optimize/agents/`。
- **修复**：optimize SKILL.md 路由表所有引用改为显式相对锚定路径 `../stk-optimize/agents/<name>.md`；analyze 侧同样处理；并在两个路由表头各加一行"本表仅指向本阶段 agents，禁止引用另一阶段同名 agent"。

### 13. analyze 路由表 markdown 结构损坏

- **证据**：`src/templates/skills/stk-analyze/SKILL.md:150-166` 子 Agent 启动条件表第 3-11 行被包进 `>` 引用块，与表头断裂；`stk-optimize/SKILL.md:78` generic 兜底行同样孤立在引用块内。
- **修复**：把表格移出引用块，恢复表头-行连续性；确认 generic 兜底行回到表格内。修复后用 `/stk` 实跑一次 analyze 验证路由可读。
