# 功能规范: 规则包 stk-rules 独立版本化，引擎只管执行

**功能分支**: `005-stk-rules-pack`
**创建时间**: 2026-09-24
**状态**: 草稿
**输入**: 用户描述: "规则包 stk-rules 独立版本化，引擎只管执行"

## 用户场景与测试 _(必填)_

### 用户故事 1 - 优化经验外置为规则包，改经验不发版 (优先级: P1)

stk 维护者发现一条新的优化经验（例如某个新插件对多数用户是低频浪费、某 MCP 有对应的更省 Token 的 CLI 替代、某个文件长度阈值需要调整）。当前这些经验写死在程序内部，每次修改都要重新构建并发布整个 stk 主程序，用户还要升级主程序才能受益。

本故事交付后：这些优化经验以**规则包**（独立版本化的数据载体）形式存在，stk 程序（引擎）只负责读取规则并执行。修改经验 = 发布新版规则包，主程序无需变动。

**优先级原因**: 这是"杀毒软件病毒库"模式的核心——优化经验的迭代速度不应被主程序发版周期锁死。没有它，其余故事都无意义。

**独立测试**: 修改规则包中的一条数据（如向低频插件名单添加一个新条目）并更新规则包版本，在不更换 stk 主程序的情况下运行诊断，验证新条目已生效。

**验收场景**:

1. **给定** stk 已安装且规则包已就位, **当** 运行诊断时, **那么** 所有判定（低频插件名单、MCP 替代映射、第三方工具目录、各类阈值）均来自规则包数据，与程序内部不再存在两份不一致的事实来源
2. **给定** 规则包发布了一个新版本（仅修改数据，主程序未变）, **当** 用户获取新版规则包后再次诊断, **那么** 新经验在诊断结果中生效
3. **给定** 规则包不存在或损坏, **当** 运行诊断时, **那么** 使用程序内置的兜底规则副本完成诊断并明确提示当前使用的是内置兜底

---

### 用户故事 2 - 一条命令更新规则库，自动检查保持最新 (优先级: P1)

用户希望像杀毒软件更新病毒库一样更新优化经验：手动一条命令可更新；平时不操心——诊断/分析启动时自动检查是否有新规则包（频率受限，例如一天最多一次），有新版则提示或静默更新。

**优先级原因**: 与故事 1 构成闭环——规则包存在后，"如何到达用户手中"决定这条链路是否真正可用。

**独立测试**: 在有新版本规则包的环境下执行更新命令，验证本地规则库升级到新版；断网环境下执行，验证不影响当前功能且给出清晰提示。

**验收场景**:

1. **给定** 本地规则库为 v1.2, 远端已有 v1.3, **当** 用户执行更新命令, **那么** 本地规则库升级为 v1.3 且命令输出显示前后版本号
2. **给定** 本地规则库已是最新的 v1.3, **当** 用户执行更新命令, **那么** 提示"已是最新"且不做任何破坏性操作
3. **给定** 距上次自动检查超过 24 小时且远端有新版, **当** 用户运行诊断时, **那么** 系统自动检查并更新规则库（或提示用户），且同一天内不重复检查
4. **给定** 网络不可用, **当** 执行更新或自动检查时, **那么** 在有限时间内失败并回退到本地现有规则，诊断功能不受影响

---

### 用户故事 3 - 多源规则叠加：内置 < 全局用户 < 项目级 (优先级: P2)

高级用户或团队希望自定义规则：个人在全局配置目录放置自己的规则覆盖默认行为；团队在项目仓库内提交项目级规则（如本项目特有的 MCP 替代策略）。多源同时存在时按明确优先级合并。

**优先级原因**: 让规则库从"官方下发"进化为"可参与、可定制"的生态基础；对单人用户非必需，故排在基础设施之后。

**独立测试**: 分别在全局与项目级放置同名规则的自定义版本，运行诊断，验证项目级优先；删除项目级后验证全局优先。

**验收场景**:

1. **给定** 内置、全局用户、项目级三层对同一条规则均有定义, **当** 在该项目的会话中运行诊断, **那么** 采用项目级定义
2. **给定** 项目级未定义、全局用户已定义, **当** 运行诊断, **那么** 采用全局用户定义
3. **给定** 仅内置定义存在, **当** 运行诊断, **那么** 采用内置定义
4. **给定** 某自定义源格式损坏, **当** 运行诊断, **那么** 跳过该源、其余源正常生效，并给出包含损坏源位置的警告

---

### 用户故事 4 - 版本兼容护栏：规则包与引擎双向声明 (优先级: P2)

规则包会声明其兼容的引擎版本区间；引擎也会校验规则包的格式版本。未来任一侧演进时，不匹配的组合被明确拒绝并降级（回退内置或旧版缓存），绝不静默产出错误诊断。

**优先级原因**: stk 的多条优化经验来自对特定平台版本的逆向分析，过期经验比没有经验更危险。护栏是规则库可持续演进的信任基础。

**独立测试**: 安装一个声明不兼容当前 stk 版本的规则包，验证诊断时该包被拒载、警告清晰、功能不中断。

**验收场景**:

1. **给定** 规则包声明兼容引擎版本 ≥ 某版本, 当前引擎低于该版本, **当** 运行诊断, **那么** 拒绝加载该包、回退内置规则，警告中同时给出两侧版本号
2. **给定** 规则包缺少版本声明或声明格式非法, **当** 运行诊断, **那么** 视为不兼容，按场景 1 处理
3. **给定** 兼容的规则包, **当** 运行诊断, **那么** 加载成功且报告中标注本次使用的规则库版本

---

### 用户故事 5 - 优化提示词随规则包分发，模板只留骨架 (优先级: P3)

stk 的分析/优化流程由安装到 AI Agent 中的技能模板驱动，其中大量"判定经验"（如何分级、某类工具在特定平台的处理方式、职责边界）目前写死在模板里。本故事交付后：这些经验性内容外置到规则包的"提示词片段"中，模板安装（初始化）时从已加载的规则包渲染生成；规则包更新后重新初始化即可获得最新经验。

**优先级原因**: 价值显著但依赖前四个故事的基础设施，且涉及模板生成方式的调整，风险与工作量更高，故最后交付。

**独立测试**: 更新规则包中某条提示词片段后重新初始化技能模板，验证安装产物包含新经验内容。

**验收场景**:

1. **给定** 已加载规则包 v1.3, **当** 用户执行技能初始化, **那么** 生成的模板中经验性章节内容来自规则包 v1.3 的提示词片段
2. **给定** 规则包不可用（缺失/不兼容）, **当** 用户执行技能初始化, **那么** 使用内置兜底提示词片段完成初始化并提示
3. **给定** 同一模板骨架, **当** 使用不同版本规则包渲染, **那么** 仅经验性章节内容不同，编排结构保持一致

---

### 边界情况

- 当**网络不可用或更新源超时**时会发生什么？→ 有限时间内失败，回退本地缓存或内置兜底，功能不中断，给出非阻塞提示。
- 当**规则包文件损坏或格式非法**时会发生什么？→ 该源整体跳过（不部分加载），回退下一优先级来源，警告指明损坏位置。
- 当**本地存在多个历史版本规则包**时会发生什么？→ 使用与当前引擎兼容的最新版本，其余保留供回退，自动清理过旧版本。
- 当**用户自定义规则与官方规则冲突**时会发生什么？→ 按"项目级 > 全局用户 > 内置"优先级取用，不做混合；冲突本身不视为错误。
- 当**规则包声明了未来引擎才支持的规则类型**时会发生什么？→ 引擎忽略不认识的规则条目并逐条警告，已认识的条目正常生效（向前兼容读取）。
- 当**诊断中途规则库被更新**时会发生什么？→ 单次诊断全程使用启动时加载的版本，更新在下次运行生效，保证单次报告内部一致。

## 需求 _(必填)_

### 功能需求

- **FR-001**: 系统必须将内置优化经验（低频插件名单、MCP 替代映射、第三方工具目录、判定阈值）全部外置为规则包数据，程序运行时从规则包读取，内部不再保留第二份可变事实来源
- **FR-002**: 系统必须在程序内内置一份兜底规则副本，在规则包缺失、损坏或不兼容时使用，保证功能始终可用
- **FR-003**: 用户必须能够通过一条显式命令将本地规则库更新到最新版本，输出须包含更新前后的版本号
- **FR-004**: 系统必须在诊断/分析启动时自动检查规则库更新，检查频率受控（默认 24 小时内至多一次），且不阻塞主流程
- **FR-005**: 系统必须支持三层规则来源（内置兜底 / 全局用户 / 项目级）并按"项目级 > 全局用户 > 内置"的优先级合并
- **FR-006**: 规则包必须携带版本清单（自身版本号、发布时间、兼容的引擎版本区间），引擎加载前完成兼容性校验
- **FR-007**: 系统必须在加载不兼容或损坏的规则源时拒绝该源并降级（回退内置或旧版缓存），给出包含原因与两侧版本号的警告
- **FR-008**: 诊断报告必须标注本次诊断使用的规则库版本号，使任意一份历史报告可追溯其经验基线
- **FR-009**: 技能模板初始化必须从当前加载的规则包渲染经验性内容（提示词片段），模板骨架与经验内容分离
- **FR-010**: 用户必须能够查看当前规则库状态（版本号、来源层、各源加载结果、最后更新时间）
- **FR-011**: 规则库更新必须支持被完全关闭（配置开关），关闭后仅使用内置兜底或用户显式放置的规则
- **FR-012**: 引擎遇到规则包中不认识的规则条目时必须忽略该条目并警告，不得中断其余规则的加载

### 关键实体 _(如果功能涉及数据则包含)_

- **规则包（Rules Pack）**: 独立版本化的优化经验载体，由版本清单（版本号、发布时间、兼容引擎区间）、数据集（名单/映射/阈值类确定性数据）与提示词片段（经验性判定知识）组成；独立于主程序发布与演进
- **规则源（Rule Source）**: 规则的一个提供方，分三层——内置兜底、全局用户目录、项目级目录；每层有明确优先级，加载结果可单独成功/失败
- **规则库状态（Rules State）**: 本机当前生效的规则库快照信息——生效版本、各源加载结果、最后检查/更新时间；供状态查询命令与诊断报告追溯使用

## 成功标准 _(必填)_

### 可衡量的结果

- **SC-001**: 修改一条优化经验（如新增低频插件名单条目）从发布新规则包到用户诊断生效，全程无需升级 stk 主程序——这是本功能存在的意义，必须成立
- **SC-002**: 断网或更新源不可达的环境下，诊断功能 100% 正常完成（内置兜底生效），无报错中断
- **SC-003**: 规则库手动更新在 10 秒内完成（正常网络环境）
- **SC-004**: 每份诊断报告均标注规则库版本号，抽取任意历史报告可回答"当时用的是哪版经验"
- **SC-005**: 人为注入损坏或不兼容的规则源，诊断不中断且警告信息可定位到具体来源
- **SC-006**: 三层来源叠加行为符合"项目级 > 全局用户 > 内置"，验证用例全部通过
- **SC-007**: 规则库相关的既有全部测试在改造后保持通过，行为无回归

## 假设与范围

### 假设（采用合理默认值）

- 自动检查频率默认 24 小时一次，且用户可关闭（见 FR-011）
- 发布渠道为单文件 URL 下载（默认仓库 raw 地址，STK_RULES_URL 可覆盖）
- 兜底规则副本随主程序一同分发，与主程序版本对齐，无需独立升级
- 提示词片段的渲染时机为技能模板初始化时（一次性渲染），不追求运行时动态注入

### 范围内

- 确定性经验数据外置（名单/映射/目录/阈值）
- 规则包版本清单与双向兼容校验
- 手动更新命令 + 受控自动检查
- 三层规则源叠加
- 诊断报告标注规则库版本
- 提示词片段外置与模板渲染

### 范围外（留待后续变更）

- 声明式检测规则引擎（match 条件 + 估算公式由引擎独立求值、脱离 AI 产出建议）
- 规则包在线浏览/搜索站点或图形化管理界面
- 社区贡献的第三方规则源订阅机制（本期仅支持本地自定义层）
